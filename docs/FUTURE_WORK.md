# 향후 과제

이 문서는 미구현 기능의 설계 계획이다. 현재 실행되는 기능은 README의 구현 현황을 따른다.

## SHAP 기반 모델 설명

### 목표

LightGBM 모델이 특정 파일의 점수를 높이거나 낮추는 데 사용한 특징 기여도를 표시한다. PE 상세정보 목록과 **모델 판단에 실제로 기여한 특징**을 구분한다.

### 구현 계획

1. 고정된 EMBER2024 특징 추출기의 각 특징 그룹·차원·오프셋을 문서화하고 합계 2,568차원을 검증한다.
2. 작업자가 모델에 보낸 것과 동일한 `float32` 특징 벡터를 설명 작업에 전달한다. 분석 후 원본을 다시 읽어 다른 벡터를 만드는 방식을 피한다.
3. 추론 서비스와 같은 모델 버전의 `shap.TreeExplainer`를 검증하고, 추가 설명 작업을 별도 큐에서 수행한다.
4. 원시 모델 출력 공간에서 기준값과 SHAP 기여도의 합이 원래 예측과 일치하는지 검사한다. 로그 오즈 기여도를 곧바로 확률 변화량으로 표시하지 않는다.
5. 악성 쪽·정상 쪽으로 영향을 준 상위 특징과 그룹별 기여도를 막대그래프 또는 워터폴로 표시한다.
6. 설명 결과는 모델·파이프라인·설명기 버전으로 별도 캐시한다. 특징 벡터를 보관한다면 접근 통제와 짧은 TTL을 적용한다.

### 해석상 제약

- EMBER 임포트 특징 일부는 해시 공간으로 표현된다. 해시 충돌 가능성을 고려하지 않고 특정 DLL/함수 하나가 원인이라고 단정하지 않는다.
- 파일명·원본 PE 항목과 특징 벡터의 매핑이 검증된 항목만 구체적인 설명을 붙인다. 그 외에는 그룹 또는 해시 버킷 수준으로 표시한다.
- SHAP은 **모델의 예측을 설명**한다. 악성 행동의 실행 증거나 인과관계의 증명이 아니다.
- 전역 feature importance를 개별 파일의 설명으로 대신 제시하지 않는다.

### 완료 기준

- 동일한 모델·벡터에서 예측 재현 및 SHAP 합산 일치 테스트 통과
- 특징 이름 매핑과 해시 충돌 표현 검토
- 추가 지연 시간·메모리 사용량 측정 및 설명 실패 시 원래 판정 유지

## 동적 분석 연계

전용 검체 저장소와 VM 기반 분석기로 확장하는 계획은 [ARCHITECTURE.md](ARCHITECTURE.md)의 미구현 파이프라인을 따른다. 현재 정적 분석 후 원본을 삭제하는 정책을 변경하려면 동의·보관·접근 제어·삭제 정책부터 함께 설계한다.

## 성능·보안 검증 확대

- 실제 Redis/PostgreSQL/Celery prefork/Docker 구성에서 큐 지연, 재시작, OOM, hard timeout을 통합 검증한다.
- 신규 요청과 캐시 적중 요청의 지연 시간을 업로드·해시·큐·특징 추출·추론·DB 단계로 구분해 측정한다.
- 1/10/100 클라이언트 부하에서 처리량·p95 지연·거절률·메모리·디스크를 함께 기록한다. 부하 시험 전 처리량 수치를 보장하지 않는다.
- 공개 서비스 전 인증·사용자별 기록 격리, TLS, Redis/DB 역할별 최소 권한, 이미지 다이제스트 고정·취약점 점검을 추가한다.
- 강한 검체 격리가 필요한 환경에는 전용 VM 또는 microVM을 검토한다. 컨테이너의 공유 커널 위험을 별도로 평가한다.
